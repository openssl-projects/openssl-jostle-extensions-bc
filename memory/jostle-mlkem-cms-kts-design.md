For [[jostle-libs-project]]: enabling CMS EnvelopedData with an ML-KEM recipient (RFC 9629).

**STATUS 2026-06-08: IMPLEMENTED and PASSING. `MLKEMEnvelopedDataTest` is no longer @Ignore — it runs and passes; the full JSL pkix suite is 82 tests / 0 failures / 0 skipped.** What's in the tree now (chosen approach: "JSL KTS cipher via reflection" — keeps the provider free of any compile-time BouncyCastle dependency):
- `org.openssl.jostle.jcajce.provider.mlkem.MLKEMKTSCipherSpi` — the KTS Cipher. `wrap`: `SpecNI.encap` → KDF3 → AES-KW, returns `encapsulation‖wrappedKey`; `unwrap`: splits at the FIPS-203 encapsulation length (512=768, 768=1088, 1024=1568), `SpecNI.decap` → KDF3 → AES-unwrap. KDF3 = `Hash(counter32‖Z‖otherInfo)` from counter 1 over a JDK `MessageDigest`. AES-KW done via a JSL `Cipher` under the AES-wrap OIDs (`2.16.840.1.101.3.4.1.{5,25,45}`). The BC `KTSParameterSpec` is read REFLECTIVELY (`getKeySize`/`getOtherInfo`/`getKdfAlgorithm`; KDF AlgorithmIdentifier DER-parsed to get the digest OID) — no `org.bouncycastle` imports in the provider. Registered in `ProvMLKEM` as `Cipher` under the ML-KEM OIDs `2.16.840.1.101.3.4.4.{1,2,3}`.
- **gap-1 RESOLVED**: `org.openssl.jostle.jcajce.provider.blockcipher.GCMAlgorithmParameters` (delegates ASN.1 codec to the JDK "GCM" `AlgorithmParameters`), registered in `ProvAES` under the AES-GCM OIDs ONLY (`id_aes128/192/256_GCM`) — NOT the bare "GCM" name (avoids self-recursion in the delegate lookup; CMS resolves by OID). This lets CMS decryption parse the stored GCM nonce/ICV.
- **gap-2 RESOLVED** (earlier): `BlockCipherSpi.validateKeyAlg` prefix-match accepts the `AESWRAP`-labelled CEK.
- **bc-jostle-libs delta**: `EnvelopedDataHelper.BASE_CIPHER_NAMES` gained the AES-GCM OIDs → "AES" (CBC OIDs were already mapped; GCM-as-CMS-content was missing, so the unwrapped CEK was mislabelled with the raw GCM OID and the strict JSL content cipher rejected it — this would also fail with SunJCE, it's a real BC gap for GCM content).
- All changes recompiled into the hot-patched jar; the durable artifact still needs a JDK-25 `:jostle:jar` rebuild (see [[jostle-jar-build-jdk25]]).

**STATUS 2026-06-06: implemented, proven working end-to-end, then REVERTED at the user's request.** The implementation is not in the tree, but it was verified to work — keep this for if it's revisited:
- Approach used (option C): JSL got its own `org.openssl.jostle.jcajce.spec.KTSParameterSpec` (wrap-name + kek-bits + otherInfo + kdf OID + digest OID — no BC types), a `MLKEMKTSCipherSpi` (encapsulate via `SpecNI.encap`/`decap`; KEK via the NIST concatenation KDF = `Hash(counter32‖secret‖otherInfo)` from counter 1, using a JDK `MessageDigest` for `id_kdf_kdf3`+SHA-256; AES key-wrap via the now-native wrap Cipher by OID; wire layout `encapsulation‖wrappedKey`), registered under `id_alg_ml_kem_512/768/1024`. The libs `JceCMSKEMKeyWrapper`/`Unwrapper` were patched to build JSL's spec (extracting kdf+digest OIDs from the BC AlgorithmIdentifier).
- **It worked**: the envelope round-tripped through encapsulate→KDF3→AES-wrap and decapsulate→KDF3→AES-unwrap. Encapsulation lengths hardcoded per FIPS 203 (512=768, 768=1088, 1024=1568) since decap can't probe ct length from a private key alone.
- **Two further gaps it surfaced** (both real, both would need handling if revisited):
  1. CMS GCM *content* decryption needs an `AlgorithmParameters` service for the AES-GCM OID on the JSL provider (to parse the stored nonce/ICV). Was solved with a small `GCMAlgorithmParameters` delegating the ASN.1 codec to the JDK "GCM" params, registered under `id_aesNNN_GCM`.
  2. ~~After content-cipher creation, init failed with InvalidKeyException because the recovered CEK is tagged with the wrap name ("AESWRAP") and JSL's AES cipher *strictly* validates `key.getAlgorithm().equals("AES")`.~~ **RESOLVED 2026-06-07 (jostle-side, as requested).** `BlockCipherSpi.validateKeyAlg` now accepts the cipher's key algorithm and its key-wrap spellings via a case-insensitive prefix match: a key whose uppercased algorithm `equals` or `startsWith` the cipher's (e.g. AES accepts `AES`/`AESWrap`/`AESWRAP`/`AESKW`) passes; a genuinely different algorithm (e.g. `ARIA` for an AES cipher) does not share the prefix and is still rejected, and key length is still validated natively. This keeps the guard tests green: `AESAgreementTest` still rejects `ARIA` ("unsupported key algorithm ARIA"); `ARIA`/`CAMELLIA` AgreementTests still reject `AES`. Verified via standalone run against the hot-patched jar + JSL pkix suite (9/9). NOTE: this fix lives only in the hot-patched `libs/openssl-jostle-1.0-SNAPSHOT.jar` until a JDK-25 `:jostle:jar` rebuild (see [[jostle-jar-build-jdk25]]).

**Original 2026-06-05 decision: DEFER — document only.** Prioritize other polish (manifests, multi-release tls, drift-checkers).

Why it's deferred (it is NOT a one-line "register a Cipher"): BC's `JceCMSKEMKeyWrapper` drives a **KTS cipher** — `Cipher.getInstance(mlkemOid).init(WRAP_MODE, pubKey, KTSParameterSpec)` then `wrap(cek)` — expecting the SPI to do **encapsulate → KDF → AES-key-wrap** and return `encapsulation ‖ wrappedKey`. To implement in JSL:
- **Encapsulate/decapsulate**: already native — `NISelector.SpecNI.encap(...)` / `.decap(...)`, exposed today via the `MLKEMKeyGenerator` KeyGenerator SPI using BC-style `KEMGenerateSpec`/`KEMExtractSpec` → `SecretKeyWithEncapsulation`.
- **KDF** (default KTS = KDF3 with SHA-256): JSL has only PBKDF2/Scrypt (`KdfNI`) and NO MessageDigest at all — would implement KDF3 in Java over a JDK SHA-256.
- **AES key-wrap (RFC 3394)**: NO LONGER A GAP as of 2026-06 — native AES-KW/KWP is implemented (`interface/util/block_cipher_ctx.c` WRAP/WRAP_PAD cases active, `EVP_CIPHER_fetch("AES-{128,192,256}-WRAP{,-PAD}")`; jostle commit `0dd67c2` "added AES-KW, AES-KWP"). The Java RFC-3394 fallback is unnecessary.
- **Contract matching**: the SPI must read BC's `org.bouncycastle.jcajce.spec.KTSParameterSpec` and `org.bouncycastle.asn1.cms.CMSORIforKEMOtherInfo` and match BC's KDF/wire format bit-for-bit.

Two reasons it's a real decision, not a quick gap: (1) ~250–350 lines of protocol crypto that must match BC exactly; (2) it would couple the *independent* OpenSSL provider to BouncyCastle ASN.1/spec classes (jostle currently has its own `org.openssl.jostle.util.asn1` and no BC dependency). Options considered: implement KTS cipher in JSL (Java KDF3 + Java RFC3394); fix native AES-KW first then KTS cipher; or handle provider-agnostically in bc-jostle-libs (custom KEM RecipientInfoGenerator using JSL's KeyGenerator KEM API). All deferred.

**STATUS 2026-06-07: re-surveyed; landscape improved, still deferred (no code added).** Of the three original blockers: (1) **native AES-KW/KWP is now done** (commit `0dd67c2`) — the hardest one; (2) **GCM OID aliases + `GCMParameterSpec` support landed** (commit `80174bb`), which largely covers the gap-1 CMS-content side, though no `AlgorithmParameters` service is registered for the AES-GCM OID yet (re-verify if revisited). The remaining substantive work is the **KTS cipher SPI itself** (~250–350 lines, encap→KDF3(SHA-256)→AES-KW, wire `encapsulation‖wrappedKey`, registered under `id_alg_ml_kem_512/768/1024`) plus the still-open **CEK key-label decision** (gap-2): `BlockCipherSpi.validateKeyAlg` strictly requires `key.getAlgorithm().equals("AES")` and `AESAgreementTest.testRejectIncorrectKeyAlgorithm` asserts that rejection, so the CMS-unwrapped CEK (tagged with the wrap name) must be re-tagged `"AES"` on the unwrap side rather than relaxing the check. Raw ML-KEM (KeyPairGenerator/KeyFactory[+OID aliases]/KeyGenerator KEM) all work today.

Note: ML-DSA/SLH-DSA signing, AES-GCM (incl. CMS content encryption via the gap-1 fix in [[jostle-provider-aes-oid-gap]]) all work today. Only the KEM *recipient* path is deferred.
