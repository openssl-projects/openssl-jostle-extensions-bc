For [[jostle-libs-project]]: brought BC's `NewSignedDataTest` (pkix CMS SignedData test, 4003 lines / 120 tests) into `bc-jostle-libs/pkix/src/test/java/org/bouncycastle/cms/test/` to run against JSL. Scope (user 2026-06-06): **prune to the JSL-supported subset** (RSA/EC/Ed/ML-DSA/SLH-DSA), drop GOST/DSA/DH/ECGOST/NTRU/RC2/SEED.

Files copied + adapted: `NewSignedDataTest`, `CMSTestUtil`, `CMSTestSetup`, `SHA1DigestCalculator`, `SHA256DigestCalculator` (cms/test), `SampleCredentials` (cert/test), `TestResourceFinder` (org/bouncycastle/test). Test data (`pkix/cms/mldsa/*.pem`) resolves via TestResourceFinder walking up to `../../bc-test-data` (auto — no -D needed).

Adaptations:
- Provider repointed BC→JSL everywhere (central `BC` constant = `JostleProvider.PROVIDER_NAME`; `new BouncyCastleProvider()`→`new JostleProvider()`; CMSTestSetup adds/removes "JSL").
- CMSTestUtil: removed GOST/DSA/DH/ECGOST/ECGOST2012/NTRU/RC2/SEED keygen init (the single eager init block aborts on first failure, so unsupported algos MUST be removed not just guarded); `ECDSA`→`EC` KPG (with init 256, not 239 — OpenSSL EC); cert/CRL converters dropped `setProvider("BC")` → JDK default X.509 factory (JSL has no CertificateFactory); content-signer/CRL signer → JSL. The unsupported `make*KeyPair`/`makeRC2*` methods + fields are kept (compile, just unused/null).
- NewSignedDataTest: removed the 2 `testLw*` BC-low-level RSA tests (used `operator.bc`/`crypto.util.PrivateKeyFactory` which were removed from the libs); converted a `BcRSASignerInfoVerifierBuilder` verify to `JcaSimpleSignerInfoVerifierBuilder().setProvider(BC)`; dropped the dead `operator.bc`/`cms.bc`/`crypto.util.PrivateKeyFactory`/`AsymmetricKeyParameter` imports.
- SampleCredentials: BC→JSL for KeyFactory; X.509 CertificateFactory → JDK default (JSL has none).

Status (2026-06-06): **compiles green and RUNS.** First full run: 103 ran, **4 pass, 99 fail** (init now completes — needed: DESede 112→192; symmetric keygens AES/DESede/Camellia wrapped in per-item try since JSL has no Camellia KeyGenerator/RC2/SEED; removed GOST/DSA/ECGOST keypair creation from init()). The 99 failures are systematic, dominated by JSL provider gaps rather than test bugs:
- **50× `CertificateException: X.509 not found`** — JSL has no X.509 `CertificateFactory`; tests route cert conversion/verification through provider "JSL" (`JcaX509CertificateConverter().setProvider(BC)`, `JcaSimpleSignerInfoVerifierBuilder().setProvider(BC).build(certHolder)`). HIGH-LEVERAGE FIX: add a JSL `CertificateFactory` SPI delegating to the JDK "X.509" (like the GCMAlgorithmParameters delegation pattern) — fixes all 50 at once.
- **20× `cannot create signer: no such algorithm: <PKCS#1 OID>`** (e.g. 1.2.840.113549.1.1.15 sha512WithRSAEncryption) — JSL registers RSA signatures by NAME but not by their PKCS#1 OIDs. FIX: alias RSA (and likely ECDSA) signature OIDs in JSL.
- **~20× NPEs** — GOST/DSA test methods using the removed keypairs (expected; prune those tests), missing test-data streams, null cert holders.
- **`SampleCredentials` NoClassDefFoundError** — its static init fails (provider/X.509 factory) → the 3 ML-DSA verify-from-vector tests.

**X.509 CertificateFactory added to JSL (2026-06-06)** — `jcajce/provider/cert/X509CertificateFactorySpi` (delegates parsing to the JDK "SUN" X.509 factory to avoid recursion) + `JSLKeyX509Certificate` wrapper whose `getPublicKey()` re-derives the key via JSL `KeyFactory.getInstance(alg,"JSL")` (because JSL Signature SPIs strictly reject foreign keys: "expected an RSAPublicKey from the Jostle provider"). Registered via `ProvX509` in `JostleProvider.configure()`. (RSA/ECDSA signature OIDs were already aliased in ProvRSA/ProvEC.) **Result: NewSignedDataTest 99 fail → 51 fail (52/103 pass).**

**Pruned 30 unsupported-algo test methods (2026-06-06)** from NewSignedDataTest (brace-matched removal by name): GOST/ECGOST/GOST2012, DSA (not ECDSA), PLAIN-ECDSA (all), RIPEMD*withRSA, sha512-224/256 withRSA, and the per-digest *withRSAPSS (JSL has only generic "RSASSA-PSS"). **Result: 51 → 21 failures (52 pass of 73).**

**Fixed-output SHAKE in ProvMD (2026-06-06)**: registered `SHAKE128-256` + `SHAKE256-512` MessageDigests (BC/CMS requests these by name as fixed-length squeezes; OpenSSL has no such digest name → map onto `new MDServiceSPI("SHAKE-128",32)` / `("SHAKE-256",64)`). **Fixed cert-holder-null cluster (2026-06-06)**: the NPE was `CMSUtils.getCertificatesFromStore` (GENERATION side, not verify) — `JcaCertStore` contained a **null** because `_signDsaCert` was never initialised (DSA keygen was pruned from `init()`). The 5 real methods (testCertOrdering1/2, testCertStoreReplacement, testEncapsulatedCertStoreReplacement, testWithAttributeCertificate) use `_signDsaCert` only as a third distinct filler cert (their signer is RSA `_origKP`); CMS preserves insertion order so cert identity is irrelevant. **Added per-digest RSASSA-PSS Signature names (2026-06-06)** in ProvRSA: `SHA1/224/256/384/512` + `SHA3-224/256/384/512` `WITHRSAANDMGF1` (each aliased to `…WITHRSASSA-PSS`). Added a digest-taking ctor `RSAPSSSignatureSpi(String digest)` (sets digest+mgf1=digest, salt=-1) because BC's OperatorHelper skips `setParameter` for DEFAULT PSS params, so the name must imply the digest. Gotcha: `addAlgorithmImplementation`'s className arg is the `creatorMap` key and must be UNIQUE — reusing `RSAPSSSignatureSpi` threw `AccessException: duplicate creatorMap key`; fixed with a `$<digest>` suffix (same trick ProvMD uses). **Cleared the 2 `testSample` PSS failures: 7→5 (now 68/73).**

**Fixed testCMSAlgorithmProtection + testRawSHA256MissingNull (2026-06-06): 5→3 (now 70/73).**
- `testCMSAlgorithmProtection`: tampered the digestAlgorithm to a *supported* digest. BC's original used `TeleTrusTObjectIdentifiers.ripemd128`, but JSL can't instantiate RIPEMD128WITHRSA so it failed at content-verifier creation before reaching the CMS-protection check under test. Swapped to `NISTObjectIdentifiers.id_sha512` (differs from the original SHA-256, and JSL has SHA512WITHRSA) → the protection check now fires on the digestAlgorithm mismatch as intended.
- `testRawSHA256MissingNull`: rawsha256nonull.p7m has an RSA PKCS#1 signature whose embedded DigestInfo omits the NULL param on the digest AlgorithmIdentifier. BC verifies it leniently; JSL/OpenSSL reconstructs DigestInfo *with* NULL and rejects the non-canonical encoding — an intentional provider-behaviour difference. Inverted the assertion to `assertFalse(...)` (with explanatory comment) to pin JSL's strict behaviour rather than prune. [If JSL ever adds lenient DigestInfo handling at the native RSA layer, this test flags it.]

**Made SampleCredentials lazy + fixed key check (2026-06-06): 3→0. NewSignedDataTest is now FULLY GREEN — 73/73 passing.**
- Converted the 7 eager `public static final` credential fields to memoised lazy accessor *methods* (`ML_DSA_44()` etc., backed by a ConcurrentHashMap). Eager init meant one missing PEM failed the whole class (ExceptionInInitializerError → cascading NoClassDefFoundError). Updated the 3 call sites in NewSignedDataTest to the `()` form.
- Laziness revealed the data was actually PRESENT; the real failure was `load()`'s sanity check `publicKey.equals(certificate.getPublicKey())`. Root cause: **JSL key impls (JOMLDSAPublicKey/AsymmetricKeyImpl and siblings) don't override equals()/hashCode()** — they use identity equality, so two instances of the same key never equals(). BC keys implement equals-by-encoding, which the original relied on. Fix: compare encoded SubjectPublicKeyInfo via `Arrays.equals(getEncoded(), getEncoded())` (provider-independent, semantically correct). Also pointed the helper's CertificateFactory at JSL (it had fallen back to JDK default when JSL lacked an X.509 factory).
- NOTE: JSL keys lacking equals()/hashCode() is a latent provider gap — other JCA consumers that key maps/sets on keys or call key.equals() will hit it. Candidate JSL improvement (add encoding-based equals/hashCode to AsymmetricKeyImpl), out of scope for this migration.

**Added equals()/hashCode() to JSL keys (2026-06-06)** in `AsymmetricKeyImpl` (shared base of all 12 JO*Key classes — RSA/EC/Ed/ML-DSA/ML-KEM/SLH-DSA public+private; the multi-release java9 EC + java15 Ed subclasses extend the SAME java/ base so they inherit it too; java17/21/25 have no key classes). Encoding-based: equal iff `getEncoded()` bytes match. Deliberately does NOT compare `getAlgorithm()` (provider-specific: JSL "ML-DSA-44" vs JDK "ML-DSA"); the SPKI/PKCS8 encoding already embeds the algorithm OID + key role. **CONSTANT-TIME for private keys** (user requirement): when either operand `instanceof PrivateKey`, the byte compare uses `MessageDigest.isEqual` (not `Arrays.equals`, which short-circuits and would leak secret key material via timing); public keys use `Arrays.equals`.

Completeness sweep (user asked re: java15/17/21/25 dirs):
- `MLDSAProxyPrivateKey` (util, implements MLDSAPrivateKey, NOT in AsymmetricKeyImpl hierarchy) — intentionally left identity-based: it's a verify-path proxy carrying NO key material (getEncoded/getPrivateData/getSeed all return empty), so encoding equality is meaningless.
- KDF SecretKeys `JOPBEKey` + `JOScryptKey` (java/, implement SecretKey, not asymmetric) — added value equals/hashCode mirroring `SecretKeySpec`: algorithm (equalsIgnoreCase) + `MessageDigest.isEqual` on the secret rawKey (constant-time).
